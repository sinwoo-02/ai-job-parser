# E2E 통합 테스트 (`test-1.ts` ~ `test-6.ts`) 명세 및 설명서

이 문서는 Playwright를 이용해 목(Mock) 없이 실제 구동 중인 백엔드 API 서버와 프론트엔드 웹 애플리케이션을 연동하여 시나리오별 예외 및 해피 케이스를 통합 검증하는 E2E 테스트 코드인 test-1.ts, test-2.ts, test-3.ts, test-4.ts, test-5.ts, test-6.ts에 대한 가이드라인 및 설명입니다.

---

## 1. 테스트 구동 방법

프론트엔드 프로젝트 루트 디렉토리(`/frontend`)에서 아래 명령어를 실행하여 테스트를 실행할 수 있습니다. 
**각 테스트 파일은 DB 상태를 순서대로 이어서 사용하므로, 개별로 실행하지 않고 반드시 아래와 같이 순차적으로 테스트해야 합니다.**

```bash
# 전체 테스트 순차 실행 (1개의 워커로 순서대로 실행하도록 강제)
npx playwright test tests/test-1.ts tests/test-2.ts tests/test-3.ts tests/test-4.ts tests/test-5.ts tests/test-6.ts --workers=1

# 특정 테스트 파일 단독 실행 (개발/디버깅 용도)
npx playwright test tests/test-1.ts
npx playwright test tests/test-2.ts
npx playwright test tests/test-3.ts
npx playwright test tests/test-4.ts
npx playwright test tests/test-5.ts
npx playwright test tests/test-6.ts

# 디버깅 및 UI 모드로 특정 파일 실행
npx playwright test tests/test-6.ts --ui

# 동적 포트/도메인(배치 채점 환경)에서 E2E 테스트 구동 (BASE_URL 환경변수 활용)
BASE_URL=http://localhost:3001 npx playwright test tests/test-1.ts tests/test-2.ts tests/test-3.ts tests/test-4.ts tests/test-5.ts tests/test-6.ts --workers=1
```

## 2. 테스트 검증 및 선택자 유연화 정책

본 E2E 테스트 시나리오들은 다양한 로컬 구동 환경 및 동료들의 서로 다른 UI 텍스트 구현체 차이를 유연하게 수용할 수 있도록 **선택자 및 텍스트 매칭 유연화 로직**이 적용되어 있습니다.

- **버튼 및 제출 폼 선택자 유연화**:
  - 버튼의 내부 텍스트가 다를 수 있음을 고려하여(예: '가입' vs '확인' vs '제출'), `button[type="submit"]` 속성을 우선 식별하거나 유사 단어 필터(예: `button:has-text("확인"), button:has-text("가입")`)를 활용한 다중 선택 방식으로 유연하게 동작합니다.
- **다이얼로그 및 경고 메시지의 정규식(Regex) 매칭**:
  - 회원가입 중복, 필수 누락 등으로 팝업되는 브라우저 Alert 및 UI 경고 메시지의 포맷 차이를 흡수하기 위해 단순 하드코딩 일치 대신 정규표현식 매칭을 적용했습니다.
    - 필수 첨부 누락 에러: `/(파일|URL).*(입력|등록)/`
    - 가입 중복 이메일 오류: `/(이미|사용.*중|중복|이메일)/`
    - 필수 데이터 누락 오류: `/(회사명|채용직무|필수|정보|모든|값을|입력)/`
- **상태 배지(Badge) 대소문자 및 한영 혼용 처리**:
  - 공고 승인 상태를 나타내는 배지 렌더링 방식이 동료들마다 상이하더라도 통과될 수 있도록 영문/한글 및 대소문자 매칭을 동시에 포괄합니다.
    - 승인 배지 검증: `/승인|완료|APPROVED/i`
    - 만료 배지 검증: `/EXPIRED|만료/i`

## 3. 테스트 실행 전 기본 전제 조건

- **백엔드 서버 구동**: 포트 `8080`에서 Spring Boot 백엔드가 구동 중이어야 합니다. (`./gradlew bootRun`)
  - 인메모리 H2 데이터베이스 초기 시드 작업으로 관리자 계정(`admin@example.com` / `1234`)이 기동 시점에 활성화되어 있습니다.
- **프론트엔드 서버 구동**: 포트 `3000`에서 Vite 개발 서버가 구동 중이어야 합니다. (`npm run dev`)
- **동적 포트 연동 (BASE_URL 환경변수)**: 
  - 기본적으로 테스트는 `http://localhost:3000` 프론트엔드를 대상으로 작동합니다.
  - 만약 `BASE_URL` 환경변수가 제공되지 않으면 `playwright.config.ts` 설정에 따라 기본값인 `http://localhost:3000`을 자동으로 사용합니다. 따라서 기본 3000번 포트 환경에서 테스트를 구동할 때에는 어떠한 환경 변수 지정 없이 기존 방식 그대로 테스트를 실행할 수 있습니다.
  - 만약 배치 테스트 스크립트나 외부 CI/CD 환경에서 임의의 다른 포트(예: `3001` 등)로 프론트엔드가 구동된다면, 실행 명령어 맨 앞에 `BASE_URL=http://localhost:3001` 형태로 환경 변수를 주입해 주어야 합니다. 
  - Playwright는 이 환경변수를 자동으로 감지하여 모든 하드코딩되지 않은 상대 경로 페이지 진입 시 자동으로 해당 호스트 및 포트에 매핑되게 처리됩니다.
- **테스트용 PDF 파일 위치**: `test-1.ts`에서 PDF AI 파싱 업로드 시나리오 검증에 사용하는 `test.pdf` 파일은 반드시 **`frontend/tests/` 디렉토리 바로 아래**에 위치해야 합니다. (전체 경로: `frontend/tests/test.pdf`)
- **실제 연동 검증**: 본 테스트는 API 모킹(`page.route()`)을 일체 배제하고 실제 네트워크 통신과 데이터베이스 트랜잭션을 수반하여 수행됩니다.
- **단일 스레드 순차 실행 (직렬 실행 필수)**: 본 E2E 테스트 파일들(`test-1.ts` ~ `test-6.ts`)은 이전 테스트에서 가공한 데이터베이스 상태를 공유하여 연속적으로 검증하므로, 병렬 실행이 아닌 **1개의 스레드(Single Worker) 상에서 차례로 실행되어야 합니다.** (Playwright 설정 파일 `playwright.config.ts`의 `fullyParallel: false` 및 `workers: 1` 설정이 강제되어 있거나, 명령 실행 시 `--workers=1` 옵션이 동반되어야 합니다.)

## 4. 테스트 케이스 명세 및 상세 검증 흐름

### 1) E2E 통합 시나리오 테스트 (`test-1.ts`)

#### (1) 일반 사용자 회원가입 테스트
* **해피 케이스: 회원가입 성공 및 리다이렉트**
  * 회원가입 폼에 이름(`user`), 중복을 방지하기 위해 생성한 타임스탬프 기반 고유 이메일, 비밀번호(`1234!`)를 입력하고 가입을 시도합니다.
  * 성공 안내 메시지(`회원가입이 완료되었습니다!`)가 노출되는지 검증하고, 약 2초 후 로그인 화면(`/login`)으로 자동 리다이렉트되는지 확인합니다.
* **예외 케이스: 이미 등록된 이메일로 중복 가입 실패**
  * `tester@example.com`으로 먼저 가입을 진행(이미 DB에 존재하면 성공 상태로 간주)하여 존재를 완전히 보장합니다.
  * 다시 회원가입 페이지에 접근하여 동일한 이메일(`tester@example.com`)로 가입 전송을 실행합니다.
  * 중복 체크 차단 문구(`이미 사용 중인 이메일입니다.`)가 팝업 에러 박스로 정상 노출되는지 검증하고, 페이지가 리다이렉트되지 않고 가입 화면에 그대로 머무는지 확인합니다.
* **예외 케이스: 필수 입력 항목(이름) 누락 시 차단**
  * 가입 정보 중 필수 입력값인 '이름' 필드를 비워두고 이메일과 비밀번호만 입력한 채 제출합니다.
  * 가입 완료 메시지가 나타나지 않으며, 페이지가 로그인 화면으로 넘어가지 않고 가입 양식에 머물러 있는지 확인합니다.

#### (2) 관리자 로그인 실패 예외 테스트
* **예외 케이스: 잘못된 계정 정보 입력 시 로그인 실패**
  * 로그인 페이지에서 올바른 관리자 이메일(`admin@example.com`)을 기입하고 비밀번호를 의도적으로 잘못 입력(`wrong_password`)하여 로그인을 시도합니다.
  * 화면에 인증 실패 메시지(`이메일 또는 비밀번호가 일치하지 않습니다.`)가 나타나는지 확인하고 로그인 페이지에 잔류함을 검증합니다.

#### (3) 관리자 데이터 세팅 및 공고 관리 테스트 (로그인 상태 필요)
* **해피 케이스: 사용자 조회, PDF 업로드 및 파싱, 삭제, 수정, 일괄 승인 변경**
  * **사용자 목록 필터링**: 관리자 권한으로 로그인 후 사용자 관리 페이지(`/admin/users`)로 이동하여, 회원가입 시나리오를 통해 가입 처리된 일반 사용자(`tester@example.com`)가 정상적으로 검색 및 리스트업되는지 테이블 텍스트를 검증합니다.
  * **PDF 공고 추가 및 AI 자동 파싱**: 공고 추가 페이지에서 로컬 테스트 PDF 파일(`test.pdf`)을 선택하여 업로드합니다. 공고 등록 클릭 시 AI 파싱 다이얼로그 확인 처리를 수행하고, 파싱이 완료되어 공고 관리 메인화면(`/jobs`)으로 정상 리다이렉트 및 데이터 로딩이 완료될 때까지 대기합니다.
  * **공고 삭제**: 파싱된 데이터 목록 중 기업명이 `SK하이닉스`인 채용 공고를 찾아서 삭제합니다. 삭제 컨펌창과 최종 삭제 알림 팝업을 통과한 후, 목록 내에 더 이상 `SK하이닉스` 관련 행이 존재하지 않는지(0개) 검증합니다.
  * **공고 수정**: 목록 내 `LG화학` 채용 공고를 찾아 연필(수정) 아이콘을 눌러 세부 수정 화면(`/jobs/edit/{id}`)으로 진입합니다. 회사명을 `연암공과대학교`로 수정한 뒤 저장합니다. 목록으로 리다이렉트되면, 검색창에 `연암공과대학교`를 검색하여 변경 사항이 정상적으로 목록에 렌더링되는지 확인합니다.
  * **일괄 상태 변경 (APPROVED)**: 검색창 필터를 초기화한 뒤, 헤더 체크박스를 통해 전체 공고를 일괄 선택합니다. `일괄 상태 변경 (APPROVED)` 버튼을 클릭하여 대기 상태(PENDING)인 공고가 모두 APPROVED 상태로 성공적으로 일괄 승인 변환되는지 배지 여부와 총 개수를 비교 검증합니다.
* **예외 케이스: 필수 첨부파일 및 URL 누락 방지**
  * 공고 추가 화면에서 어떠한 첨부파일이나 웹사이트 URL을 입력하지 않은 상태로 공고 등록을 제출합니다.
  * 브라우저 경고 팝업(`공고 파일 업로드 또는 웹사이트 URL 중 최소 하나는 입력해 주셔야 합니다.`)이 트리거되며 등록 절차가 제한되는지 검증합니다.
* **예외 케이스: 공고 상세 수정 중 필수 파라미터 누락 방지**
  * 특정 공고의 수정 페이지로 접근하여 필수 입력 정보인 '회사명' 필드를 완전히 비운 채 수정을 저장하려고 시도합니다.
  * 필수값 누락 경고 다이얼로그(`회사명과 채용직무는 필수 정보입니다.`)가 팝업되며 수정 내용 저장이 거부되고 수정 페이지에 그대로 복귀되는지 확인합니다.

### 2) 관리자 로그인 및 모바일 반응형 레이아웃 테스트 (`test-2.ts`)

#### (1) 관리자 로그인 성공 및 반응형 레이아웃 테스트
* **해피 케이스: 로그인 성공, 햄버거 메뉴 작동, 가로/세로 레이아웃 반응형 변환 검증**
  * 로그인 페이지에서 지정된 관리자 계정 정보(`admin@example.com` / `1234`)를 기입하고 제출합니다.
  * 정상적으로 로그인되어 메인 대시보드 화면(`/`)으로 이동하고 "대시보드 요약" 헤더가 노출되는지 검증합니다.
  * **PC 화면(기본 뷰포트) 검증**: 767px 초과 해상도에서는 햄버거 메뉴 버튼이 화면에서 숨겨져 있고, 대시보드 벤토 요약 카드들이 서로 다른 x축 위치에 나란히 가로 배열(row)되어 있는지 카드들의 Bounding Box 좌표를 이용해 검증합니다.
  * **모바일 화면(767px 이하 뷰포트) 검증**: 화면 너비를 767px로 조절한 뒤 햄버거 메뉴 토글 버튼이 정상적으로 노출되는지 검증합니다. 햄버거 메뉴를 클릭했을 때 드로어 사이드바가 열리는지(`.side-nav-bar.open`) 및 백드롭 영역 클릭 시 정상 닫히는지 작동 여부를 검증합니다. 또한 대시보드 요약 카드들의 Bounding Box x축 좌표가 일치하고 y축으로 나란히 수직 정렬되는 세로 배열(column) 전환 상태를 최종 검증합니다.
  * 데스크톱 화면으로 원복하여 로그아웃 버튼을 클릭하고 다시 로그인 페이지(`/login`)로 안전하게 되돌아가는지 검증합니다.

#### (2) 관리자 로그인 실패 및 입력값 누락 제어 검증
* **예외 케이스: 비밀번호 불일치 시 로그인 실패**
  * 아이디는 동일하게 `admin@example.com`을 입력하고 비밀번호를 잘못된 문자열(`wrong_password`)로 작성하여 제출합니다.
  * 화면에 에러 문구(`이메일 또는 비밀번호가 일치하지 않습니다.`)가 출력되는지 검증하고 페이지 리다이렉트 없이 로그인 페이지에 머무르는지 확인합니다.
* **예외 케이스: 미가입 계정으로 로그인 시도 시 실패**
  * 가입된 적이 없는 미등록 이메일 주소(`nonexistent_admin@example.com`) 및 비밀번호(`1234`)를 기입하여 로그인을 제출합니다.
  * 서버에서 반환되는 인증 에러 팝업 메시지를 검증하고 로그인이 거부됨을 확인합니다.
